PHASE 6: IMAGE UPLOADS AND FILE HANDLING
                              →  /audit/06-uploads.md
═══════════════════════════════════════════════════════════
This area has never been audited. Test every upload path in
the product:
  vendor logo and cover image
  menu item photos
  compliance document upload (insurance, certificates, ID)
  menu photo upload for assisted build, if implemented
  any customer-side upload (review photos, dispute evidence)
  generated files: QR codes, payout statement PDFs, catering
    compliance packs, terms acceptance PDFs

For EACH upload path test:
  FORMATS: jpg, png, webp, and HEIC specifically. iPhones
    shoot HEIC by default and vendors will upload from phones.
    If HEIC fails, that is a major finding.
  PDF where documents are expected.
  EXIF ORIENTATION: upload a portrait photo taken on a phone
    and confirm it does not render sideways. This is a classic
    failure and vendors will notice immediately.
  SIZE: a large file (10MB+) and confirm either it is accepted
    or rejected with a clear message, never a silent failure
    or a timeout.
  ZERO-BYTE file, and a file with a mismatched extension (a
    .txt renamed to .jpg). Both should be rejected cleanly.
  SVG: confirm SVG uploads are either rejected or sanitised.
    An SVG can carry script.
  REPLACE and DELETE: upload, replace, delete. Confirm the old
    object is removed and no broken reference remains.

Storage and access control, this is the security part:
  Confirm each file lands in the expected Supabase Storage
    bucket.
  PRIVATE DOCUMENTS MUST BE PRIVATE. Take the URL of an
    uploaded compliance document (insurance certificate, photo
    ID) and attempt to fetch it while signed out and from a
    different vendor's session. If it is retrievable, that is
    a critical finding. Report the exact URL pattern, not the
    document contents.
  Confirm public images (menu photos, logos) ARE publicly
    reachable, since a broken image on a listing costs orders.
  Check whether uploaded filenames are sanitised or used raw.

Rendering: after each upload, confirm the image actually
displays where it should, at the correct aspect ratio, on both
desktop and mobile, and that a missing image degrades to a
sensible placeholder rather than a broken icon.

PHASE 9: THE REPORT
       →  /audit/FEASTPOT_READINESS_<YYYY-MM-DD>.txt
═══════════════════════════════════════════════════════════
Plain text. No markdown syntax, no tables, no emoji. Wrap at
78 characters. UK English. No em dashes anywhere.

Structure:

  FEASTPOT LAUNCH READINESS AUDIT
  <date>

  Purpose
  -------
  What was covered, how, and the commit SHA audited.

  Verdict
  -------
  Six to ten lines. Is this platform ready for real vendors,
  real customers and real admin staff? Answer plainly. If not,
  name the small number of things that must be true first. Do
  not hedge.

  Blockers - Must Fix Before Any Real User
  -----------------------------------------
  For each:
    <n>. <One line stating the problem as fact>
    Why this matters: plain-language consequence.
    Evidence: file:line with a short excerpt, or the command
      and its real output, or the screenshot path.
    What to implement: specific and actionable.

  Fix Within The First Weeks
  --------------------------
  Same format.

  Housekeeping
  ------------
  Same format, briefer.

  Confirmed Working
  -----------------
  Only things you actively exercised. This tells me where NOT
  to spend effort, so it matters as much as the problems.

  Not Verified
  ------------
  Everything you could not test and why. Be exhaustive. A
  reader must be able to tell exactly where this audit's
  knowledge ends.

  Coverage
  --------
  Routes visited versus routes existing, per app. Upload paths
  tested versus upload paths existing. Tests executed.

RANKING RULE
Order by consequence multiplied by likelihood. Food safety,
money loss and legal exposure outrank everything. A cosmetic
issue ranks last however easy it is to fix. Do not rank by
ease of fixing.

TONE
Write for a founder making launch decisions, not for
engineers. Plain language. No softening. If something is bad,
say it is bad.

FINAL CHECKS
  Every finding has real evidence. Delete any you cannot
    evidence.
  No secret values anywhere in the file.
  No em dash characters anywhere in the file.
  The Not Verified section is complete and honest.
  You fixed nothing.

Then give me a five-line summary in chat plus the blocker
count. Do not begin fixing anything.
