CONTEXT
Feastpot Turborepo monorepo. apps/admin is a Next.js 15 App Router admin panel. apps/api is NestJS 11. Prisma against Supabase Postgres. Stripe Connect for payments. packages/config exports PLATFORM_FACTS, packages/ui exports shared components, packages/types exports Zod schemas and re-exported Prisma types. UK English. Never use an em dash or a double hyphen used as a dash anywhere.

THIS IS A READ-ONLY AUDIT. Do not write, edit, delete or refactor any code. Do not add stubs, TODOs or placeholder implementations. Do not "fix while you are there". Your only output is a report. If you find something alarming, report it prominently rather than repairing it.

EVIDENCE RULE: every verdict must cite at least one file path, and where useful a line range. A verdict with no cited evidence is not acceptable. Where you cannot determine something without running the app, say so explicitly and state the exact manual check required. Never infer that a feature works from its presence in navigation, marketing copy, seed data, a comment, or a type definition.

=====================================================================
PHASE 1: ACCESS CONTROL AND SECURITY (do this before anything else)
=====================================================================
The admin panel can presumably approve vendors, issue refunds, read customer data, create discount codes and suspend accounts. It is the highest-value target in the product. Audit it as such.

1. AUTHENTICATION. The apps/admin root layout is understood to be a bare shell of roughly 30 lines containing only html, body, QueryProvider, Toaster, Analytics and SpeedInsights, with no nav and no visible auth wrapper. Determine precisely how an unauthenticated visitor is prevented from loading an admin route. Check for middleware.ts, a layout-level guard, per-page server-side checks, or an API-level guard. Report the mechanism, or report plainly that there is none.
2. AUTHORISATION. Determine how a signed-in but non-admin user (a customer or a vendor) is prevented from using admin functions. Is there a role claim, a database role table, an allowlist? Is it checked on the client, the server, or both? A client-only check is not a control.
3. API-LEVEL ENFORCEMENT. For every admin endpoint found in Phase 0, state whether it independently verifies the caller is an admin, or whether it trusts the caller because the request came from the admin app. Test the assumption: could the endpoint be called directly with a normal user's token? Report each endpoint as GUARDED or UNGUARDED with the file and line of the guard.
4. RLS INTERACTION. Determine whether admin reads and writes go through the service_role key (bypassing RLS entirely) or the user's own token. If service_role is used, confirm it is only ever used server-side and never reaches the client bundle. Grep the built output for the service key pattern and report the result.
5. AUDIT TRAIL. Determine whether consequential admin actions (suspending a vendor, issuing a refund, changing a discount code, approving an application, editing verification state) record who did them and when. Report which actions are logged and which are not. An admin panel without an audit trail is a problem in its own right.
6. DESTRUCTIVE ACTIONS. List every admin action that moves money, suspends an account, or deletes data, and state for each whether it has a confirmation step and whether it is reversible.

Report Phase 1 findings FIRST in your summary, before any feature verdicts. If you find an unguarded admin endpoint or a service key exposed client-side, say so in the first paragraph.

PHASE 2: FEATURE VERDICTS

For each capability below, and any others you discover, assign exactly one verdict:

  SHIPPED     UI, API and data layer are connected, reachable by a real admin action, AND covered by a passing automated test.
  WORKING     As SHIPPED but with no automated test coverage.
  PARTIAL     Some layer exists but is not connected end to end, for example a UI control with no backend behind it, a service never called, or a hardcoded or mocked response.
  STUBBED     Present only as a comment, TODO, or unused scaffold.
  MISSING     Not found anywhere.

For each, report: verdict, evidence (file paths), what is missing if not SHIPPED, test coverage, and whether an admin could rely on it today.

PHASE 3: EVERY CONTROL HAS AN OBSERVABLE EFFECT
=====================================================================
Four features in this product have been found that render and do nothing. Apply the generalised check here.

Enumerate every interactive control in apps/admin: every button, toggle, filter, dropdown, form field and bulk action. For each, trace whether changing it produces an observable, correct consequence: a state change, an API call that reaches a real handler, a database write, or a visible UI update driven by real data.

Produce a table: control | location | traced effect | verdict (REAL, NO-OP, UNTRACEABLE WITHOUT RUNNING).

Name every NO-OP explicitly. This list is the most valuable output of the audit.

=====================================================================
PHASE 4: PERFORMANCE
=====================================================================
The database is currently near-empty, so nothing will feel slow today. Assess against realistic future volumes: 500 vendors, 50,000 orders, 200,000 order items, 20,000 customers.

1. PAGINATION. For every admin list view, determine whether it paginates server-side, paginates client-side after fetching everything, or fetches everything with no pagination at all. A list that does findMany with no take will eventually time out. Report each list with its current behaviour.
2. N+1 QUERIES. Inspect every admin data path for queries inside loops, or Prisma calls lacking include or select where a relation is then accessed per row. Cite each instance.
3. OVER-FETCHING. Identify queries selecting whole rows where a handful of columns are displayed, particularly on tables with large text or JSON columns.
4. INDEXES. For every column used in an admin WHERE, ORDER BY or JOIN, check whether prisma/schema.prisma declares an index. List columns that are filtered or sorted but unindexed. Pay attention to status enums, created_at ordering, and any foreign key used for admin filtering.
5. AGGREGATES. Identify any count or sum computed by fetching rows and counting in JavaScript rather than in the database.
6. CLIENT BUNDLE. Report the admin app's bundle size, any large dependency, and whether heavy components are dynamically imported. An internal tool can tolerate a larger bundle than a customer app, so weight this finding accordingly rather than treating it as critical.
7. RENDERING. Identify lists rendered without virtualisation that could exceed a few hundred rows, and any component re-rendering on every keystroke of a search field with no debounce.
8. REALTIME AND POLLING. Identify any polling interval or realtime subscription, and state its cost at scale.

For each finding, state the volume at which it becomes a real problem, so the list can be prioritised rather than treated as uniformly urgent.
