PART 2: ONE CATERING SURFACE, WITH THE SLA MADE VISIBLE
=====================================================================
Three admin pages cover one product: Events (event enquiries and quotes), Catering
Enquiries (the two live records, with the assign flow), and Catering bookings (a
metrics page that loads nothing until a manual Search click). An admin cannot know which
page is the source of truth, and the two real enquiries sit in only one of them.

1. INSPECT FIRST: read the three pages and their backing endpoints. Establish whether
   Events and Catering Enquiries are two views over the same tables or two parallel data
   models. Report what you find; the merge plan depends on it. If they are parallel
   models, additionally report which one the customer-facing /catering form writes to.
2. MERGE into a single Catering section with tabs: Enquiries (the triage and assign
   queue), Bookings (assigned work and its lifecycle), and Performance (the metrics
   currently on Catering bookings). Retire the two absorbed routes with redirects.
3. SLA URGENCY. The page states assignment within 48 hours. Make that claim operational:
   - Each enquiry row shows time since received and a status pill that turns amber at
     24 hours and red past 48, reading "Overdue by Nh".
   - Rows with an event date inside 7 days show a separate "Event in N days" flag,
     red inside 72 hours.
   - Default sort: most urgent first, by the earlier of SLA breach and event proximity.
   - The dashboard gains one line in the status strip when any enquiry is overdue or has
     an event inside 72 hours, linking to the queue. An SLA that only exists as a
     sentence in a page subtitle is not an SLA.
4. The assign action must be available directly from the row, not only behind Review.
5. Bookings and Performance tabs load their data on mount. Remove the click-Search-to-
   load pattern.

PART 3: OPERATIONAL REPAIRS
=====================================================================
1. COMPLIANCE CRON. Three dead-lettered review-trigger jobs on the compliance queue:
   one "Job repeat ... is not in the active state. finished" and two "job stalled more
   than allowable limit". Diagnose properly:
   - Inspect how the repeatable job is registered. The repeat-key error usually means
     the job is being re-registered with a changed key or removed while an instance is
     mid-flight; make registration idempotent (remove-then-add with a stable key, or
     upsert semantics).
   - The stalled errors mean the worker held the job past the stalled interval, usually
     a long-running handler or an event-loop block. Measure what the handler does,
     move heavy work into batched steps, and set a stalledInterval and lock duration
     that fit its real runtime.
   - After the fix, retry the dead-lettered jobs, confirm they complete, and confirm the
     next scheduled run executes on time. Report the schedule and the last successful
     run timestamp.
   - Add an alert: if the compliance cron misses a scheduled run or dead-letters again,
     Slack fires. A silent compliance checker is the same defect as a silent seed.
2. ADMIN SHELL. The Dead-letter Bull jobs page renders without the sidebar and shell.
   Wrap it in the same layout as every other admin page, and add a Playwright assertion
   that every route under apps/admin renders the shell (walk the route list, assert the
   sidebar exists). That guard catches the next page that forgets.

PART 4: ANALYTICS AND METRIC INTEGRITY
=====================================================================
1. SEARCH TREND FRAGMENTS. The dashboard trends include "P" and "Pu": the customer app
   logs a search event per keystroke. Fix at the source in apps/web: log a search event
   only when the query has settled (debounced at least 500ms since last keystroke) AND
   is at least 3 characters, and log at most one event per settled query per session
   window. Then clean the stored data: delete or flag existing single- and two-character
   fragment events, and recompute any recruitment-opportunity counts derived from them.
   Report how many rows were cleaned.
2. ZERO-DENOMINATOR HONESTY. FeastPass health shows "Monthly renewal rate 100.0%,
   north-star metric" with zero members, and churn "0.0%, 0 of 0 subs". Any ratio whose
   denominator is zero renders as "No data yet", never as 100% or 0%. Apply the same
   rule everywhere a ratio renders in apps/admin (renewal, churn, repeat rate, success
   rate, funnel percentages). Grep for toFixed and percentage formatting to find them
   all, and route them through one shared formatter that takes numerator and
   denominator.
3. FUNNEL OVER 100%. Vendor acquisition shows "Calculator used, 36 events, 100.0% of
   page views" against 26 page views. Do not cap. Show the true ratio with a clarifying
   label (events per session where events can exceed sessions), or compute the
   percentage on unique sessions only and label it so. Pick one, label it honestly,
   state the choice.
4. DASHBOARD COUNTS. After Part 1, confirm active vendors, GMV and orders derive only
   from real records. Add a test asserting the dashboard vendor count equals the count
   of live, non-seed vendors in the database.
