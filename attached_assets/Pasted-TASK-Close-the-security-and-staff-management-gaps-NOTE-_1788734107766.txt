TASK: Close the security and staff-management gaps.

NOTE: setting ADMIN_REQUIRE_AAL2 and enrolling the admin
account is in FP-01. This prompt covers what the UI must do.

S1. ENFORCEMENT MUST FAIL CLOSED
apps/api/src/main.ts:143-155 writes a warning and CONTINUES
BOOTING when ADMIN_REQUIRE_AAL2 is not exactly true in
production. Make it refuse to boot. A misconfiguration must
be a failed release, not a log line. Same for the admin gates
at middleware.ts:76-93 and server-gate.ts:82-89.
The /settings security card must show the PLATFORM
enforcement state, not only whether the current user has 2FA
enabled. If enforcement is on and a staff member is not
enrolled, block them at sign-in with a clear enrolment path.

S2. ROLE MANAGEMENT IN THE UI
/settings states: "Promoting a customer to a staff role is
currently a database operation. Contact engineering." For a
solo founder that means contacting themselves. This is a
missing feature described as a process.
Build it: from /users, change a role among admin, support,
finance, compliance, or back to customer. Require a written
reason recorded to the audit log with actor, target, previous
and new role. Require an AAL2 session. Prevent the last
remaining admin from demoting themselves. Show which staff
have MFA enrolled.

S3. ENFORCE THE DOCUMENTED ROLE MATRIX
/user-guide documents four roles and precisely what each can
access; /settings repeats it. The sidebar shows everything
regardless. Enforce in navigation AND verify server-side.
Documentation is not enforcement.

S4. JOB QUEUES BYPASS THE ADMIN SESSION
"Job queues" opens api.feastpot.co.uk/admin/queues with a
browser-native HTTP Basic Auth dialog. That means a second
credential set outside Supabase auth, MFA not applied, no
attribution in the audit log, and the operator leaving the
console. Anyone holding those credentials reaches queue
controls without an admin account.
  Preferred: proxy Bull Board behind the admin app's own
  authentication, validating the session and AAL2
  server-side. Remove Basic Auth entirely. Log access.
  Fallback: replace Basic Auth with a short-lived signed
  token issued to an authenticated AAL2 admin, in an embedded
  frame rather than a new tab.
Either way, add a compact in-app queue health panel showing
per queue: waiting, active, delayed, failed, and oldest
waiting job age, wired to the same data as the queue depth
monitor so alerts and visible numbers agree.

S5. PLATFORM DEFAULTS NOTE
"Editing these defaults requires a backend release. Open an
engineering ticket." Payout cadence and currency are
reasonably code-level; commission is not and after FP-04
reads from the engine anyway. Reword to say precisely which
values are code-level and why. Remove the ticket language.

S6. ROLE MATRIX TESTED, NOT READ
Using FP-09 factory tokens, assert: every admin endpoint with
a vendor token 403; with a customer token 403; every vendor
endpoint with another vendor's token 403; vendor A cannot
read vendor B's orders, payouts, menu, documents, disputes or
tax profile; an AAL1 staff session is rejected; an AAL2
session is allowed.

S7. ERROR INCIDENT ATTRIBUTION
POST /v1/error-incidents is public by design but accepts
vendorId and userId from the client and persists them as
authoritative. An audit proved spoofing with a real vendor ID.
Derive identity from the session when present; for anonymous
reports persist NO ownership relationship. Keep client values
only as sanitised non-authoritative diagnostic context.
Also verify the error reference (e.g. "Ref: 4121942664") is a
real persisted identifier support can look up. If cosmetic,
make it real (format distinctly, persist with stack trace,
route and timestamp) or remove it.

ACCEPTANCE CRITERIA
- Production refuses to boot without MFA enforcement.
- A role change is possible from /users with reason and AAL2.
- The last admin cannot demote themselves.
- No static Basic Auth credential remains.
- The full role matrix is asserted with real tokens.
