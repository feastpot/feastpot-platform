MANDATORY PRODUCT DECISION (implement exactly this, do not deviate):

A. TWO SEPARATE CONCEPTS. Split the single conflated "dietary" filter into two distinct, separately named query concepts:
   - dietaryPreferences: lifestyle choices. Allowed values ONLY: "vegan", "vegetarian". These are NOT safety claims.
   - allergenFree: absence-of-allergen filters keyed to the FSA 14. Allowed values ONLY (canonical, lower-case, hyphenated): "celery", "cereals-containing-gluten", "crustaceans", "eggs", "fish", "lupin", "milk", "molluscs", "mustard", "nuts", "peanuts", "sesame", "soya", "sulphur-dioxide". The customer UI labels map to these (for example the existing "gluten-free" checkbox maps to "cereals-containing-gluten"; "nut-free" maps to BOTH "nuts" and "peanuts"; "dairy-free" maps to "milk").
   Store these canonical values as an exported constant in packages/config so the customer UI, the DTO validation, and the repository all read from one source. Add or extend the platform-facts.spec.ts consistency test so CI fails if the allergen value list drifts.

B. POSITIVE FILTER SEMANTIC (this is a safety decision, implement exactly). "allergenFree=nuts" MUST mean: return vendors that have AT LEAST ONE menu item whose declared allergens do NOT include "nuts" (and "peanuts"). It MUST NOT mean "exclude every vendor whose menu contains any nut dish", and it MUST NOT mean "this vendor is nut-free". A vendor appears if they have one or more matching dishes. Never make an absence-of-allergen claim about a whole vendor or kitchen.

C. NULL/EMPTY HANDLING. A menu item with an empty or NULL allergens array means "allergen information not provided", NOT "free from all allergens". Items with no declared allergen data MUST NOT satisfy an allergenFree filter. Treat missing data as unsafe/unknown, never as safe.
