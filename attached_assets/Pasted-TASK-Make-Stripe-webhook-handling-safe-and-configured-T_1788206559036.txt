TASK: Make Stripe webhook handling safe and configured.

TWO DEFECTS, ONE OF WHICH BLOCKED THE AUDIT

D1. THE RACE
apps/api/src/modules/payments/stripe-webhook.controller.ts
sequence is: check ProcessedWebhookEvent exists, enqueue the
job, then insert the processed-event row. Stripe guarantees
at-least-once delivery, so two concurrent deliveries of the
same event can both pass the check and both enqueue. Only the
second insert is rejected, by which time the work is queued
twice.

Fix: claim the event ID atomically BEFORE queueing. Insert
the ProcessedWebhookEvent row first and treat a unique
constraint violation as "already accepted, return 200". Then
enqueue. Add a recoverable path for "claimed but enqueue
failed" so an event cannot be permanently swallowed, for
example a claim status column plus a sweeper for stale claims.

D2. THE ENVIRONMENT
The audit's signed probe returned 503 WEBHOOK_NOT_CONFIGURED,
so the concurrency test could not run at all. The workspace has
STRIPE_WEBHOOK_SECRET_LIVE but no test secret, and the app
correctly fails closed in non-production mode. Resolve the
environment-specific secret in every deployment, and document
which secret each environment uses. Then verify a signed test
event is accepted.

D3. account.updated
Absent from stripe-webhook.events.ts:15-31. Unhandled events
are only warned about at controller:104-125. Add it, map
capability and requirement fields to the vendor record, audit
the change, and alert when payout capability is lost.

Assert the ACTUAL observed counts, not intended behaviour.
