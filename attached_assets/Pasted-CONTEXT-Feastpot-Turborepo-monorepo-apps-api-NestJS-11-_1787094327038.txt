PART 1: D-001, MAKE THE WRONG REFUND PATH IMPOSSIBLE
=====================================================================
1. INSPECT: locate the admin status-override path that calls Stripe refund directly
   (found by the audit in the order status-override handling). Report the file, line and
   exactly which Stripe call it makes.
2. REMOVE the direct Stripe call from that path entirely. A status override must never
   move money. If the override flow legitimately needs to offer a refund (for example
   overriding to cancelled on a paid order), it composes the existing
   POST /v1/admin/orders/:orderId/refunds service method, so every refund flows through
   the single implementation with its commission reversal, allowance restoration,
   Refund record and AuditLog row.
3. In the admin UI, if the override dialog implied a refund would happen, either wire it
   to the real refund flow with the standard confirmation, or remove the implication.
   The UI must not promise money movement the endpoint no longer performs.
4. GUARD AGAINST REINTRODUCTION: add a lint-style CI check (extend the existing
   check-claims.mjs pattern) that fails if stripe.refunds.create or equivalent appears
   anywhere outside the single refunds service module. Allowlist that one module with a
   comment. This is the same discipline as the banned-strings guard: the invariant is
   "one refund path", so enforce it mechanically.
5. TEST: drive a status override to cancelled on a paid seeded order and assert:
   no Stripe refund occurs unless the refund flow was explicitly invoked; when it is
   invoked, commissionPence reverses, allowance restores, a Refund row and an AuditLog
   row exist. Then grep-assert the CI guard catches a deliberately added rogue call.

PART 2: D-002, MAKE ALLOWANCE RESTORATION ATOMIC
=====================================================================
1. INSPECT: locate the refund handling where commission reversal and founding-allowance

PART 3: D-003, GUARD THE COMMISSION BACKFILL
=====================================================================
The calculate() backfill recomputes commission from the raw subtotal, ignoring vendor-
funded discounts and founding allowance. Running it on such orders would overwrite correct
figures with wrong ones.
1. Make the backfill refuse orders it cannot compute correctly: if the order has a
   vendor-funded discount or consumed allowance, skip it and count it in the run summary
   as skipped_unsafe, rather than recomputing. It may only recompute orders whose inputs
   match its assumptions.
2. Better, if the stored values needed are present (discountFundedBy, allowance applied
   pence on the order), teach it to compute correctly from those stored values and remove
   the restriction. Choose based on what the Order row actually stores; state the choice.
3. Add a dry-run mode that prints what would change without writing, and make dry-run the
   default. A backfill that writes by default is how correct data gets destroyed.
4. TEST: the backfill on the seeded world changes nothing (all orders were computed by
   the live engine), and a deliberately corrupted copy of a plain marketplace order is
   corrected while a vendor-discounted order is skipped or correctly recomputed per your
   choice in step 2.
